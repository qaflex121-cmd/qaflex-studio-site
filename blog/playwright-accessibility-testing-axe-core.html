Practical Accessibility Testing with Playwright and axe-core

Turn automated accessibility scans into actionable regression checks without confusing a clean scan with full accessibility.

QAFlex Studio · 21 November 2026 · 9-minute read

Accessibility testing is most useful when it checks the states people actually encounter: an initial page, a validation error, a modal dialog, a filtered result list, and a completed workflow. Automated rules can catch many programmatically detectable issues, but they cannot determine whether every interaction is usable with a keyboard or assistive technology. A good strategy combines repeatable scans with deliberate manual checks.

1. Choose meaningful user journeys

Begin with a small set of high-impact experiences rather than scanning every URL indiscriminately. Include sign-in, navigation, forms, search, data tables, and any complex component your product relies on. For each journey, identify the states that change accessibility behaviour.

  • Initial render: landmarks, headings, labels, and document structure.
  • Interaction state: menus, dialogs, accordions, and dynamic results.
  • Error state: required-field errors, invalid inputs, and error summaries.
  • Responsive state: narrow layouts and zoom, where applicable.

Use a risk-based approach: prioritize components used across many pages, flows required to complete essential tasks, and areas with known accessibility defects.

2. Install the Playwright integration

In an existing Playwright Test project, install the axe-core integration as a development dependency:

npm install --save-dev @axe-core/playwright

The following example uses Playwright Test and @axe-core/playwright. It assumes the application is available at a configured baseURL.

import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('sign-in page has no detected WCAG A/AA violations', async ({ page }) => {
  await page.goto('/login');
  await expect(page.getByRole('heading', { name: 'Sign in' }))
    .toBeVisible();

  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa', 'wcag22aa'])
    .analyze();

  expect(results.violations).toEqual([]);
});

The tags select the rules associated with those WCAG conformance levels in the installed axe-core version. They are not a guarantee of WCAG conformance. Pin dependency versions through your lockfile and review rule changes during upgrades.

3. Scan after the UI reaches the intended state

A scan performed before a dialog opens cannot detect problems inside that dialog. Trigger the interaction, assert that the intended state is visible, and then analyze the page.

test('account dialog accessibility', async ({ page }) => {
  await page.goto('/settings');
  await page.getByRole('button', { name: 'Edit profile' }).click();

  const dialog = page.getByRole('dialog', { name: 'Edit profile' });
  await expect(dialog).toBeVisible();

  const results = await new AxeBuilder({ page })
    .include('[role="dialog"]')
    .analyze();

  expect(results.violations).toEqual([]);
});

This example scopes analysis to the dialog. Use a full-page scan as well when you need to assess relationships with surrounding content, such as whether background elements remain accessible while a modal is open. Scoping can reduce noise but can also miss issues outside the selected subtree.

4. Make failures diagnosable

A raw assertion failure may hide the affected nodes. During triage, record each rule identifier, impact, help URL, and the failing node's target. Keep logs free of sensitive form values and user data.

const results = await new AxeBuilder({ page }).analyze();

const summary = results.violations.map(v => ({
  rule: v.id,
  impact: v.impact,
  help: v.helpUrl,
  targets: v.nodes.map(node => node.target)
}));

console.log(JSON.stringify(summary, null, 2));
expect(results.violations).toEqual([]);

For each finding, reproduce it, inspect the relevant markup, and determine whether the underlying issue belongs in a shared component or an individual page. Capture a minimal reproduction and the expected accessible behaviour in the defect report.

5. Handle existing violations without hiding new ones

Legacy applications may already have a backlog. Avoid permanently disabling entire rule families just to make CI green. Instead, record known issues with owners and deadlines, fix shared-component defects first, and maintain a clearly reviewed baseline. Any exclusion should be narrow, documented, and revisited. A baseline is a temporary management tool, not evidence that the product is accessible.

Do not use an exclusion to suppress a serious defect in a critical journey. Where you must exclude a third-party widget you cannot modify, document the vendor dependency and verify the surrounding flow manually.

6. Run accessibility checks at the right CI stage

Start with a fast smoke set for essential journeys on pull requests. Run a broader set for important states on a scheduled or release pipeline. Publish useful failure evidence, but avoid printing secrets or storing sensitive page content in artifacts. If your CI runs in parallel, isolate test accounts and data as you would for other Playwright tests.

Track meaningful measures: number of new violations, age of known violations, critical journeys covered, and recurring component-level defects. A count of passing scans alone does not measure accessibility quality.

7. Add manual testing that automation cannot replace

  • Complete core journeys using only the keyboard; inspect focus order and visible focus indicators.
  • Check that focus moves into dialogs and returns sensibly when they close.
  • Use a screen reader to confirm names, roles, instructions, and status announcements are understandable.
  • Review text alternatives for meaning, not just presence.
  • Check zoom, reflow, error recovery, and content clarity.
  • Include people with disabilities in usability evaluation when possible.

Automated scans can identify some violations; manual and assistive-technology testing are necessary to evaluate the experience beyond the rules that tools can detect.

Implementation checklist

  • Select critical journeys and their interactive states.
  • Install and lock compatible Playwright and axe-core packages.
  • Wait for a meaningful UI state before each scan.
  • Keep page-wide coverage alongside targeted component scans.
  • Attach rule IDs and affected targets to defect reports.
  • Review exclusions and known-issue baselines regularly.
  • Combine CI scans with keyboard, screen-reader, and zoom testing.
