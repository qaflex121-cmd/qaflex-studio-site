How to Reduce Flaky Playwright Tests

Use evidence to find the reason a test is intermittent before adding retries or longer timeouts.

QAFlex Studio · Automation engineering · 7-minute read

A flaky test passes and fails without a relevant product change. It creates noise in CI, reduces confidence in regression results, and costs engineers time. The goal is not simply to make the test pass once; it is to identify and remove the unstable assumption.

1. Classify the failure before changing the test

Start with the error, trace, screenshot, browser console, and network activity. Put the failure into a likely category:

  • Locator instability: the selector matches multiple elements, depends on layout, or targets an implementation detail.
  • Timing assumption: the test acts before the application reaches the expected state.
  • Shared state: another test or an earlier run changes data the test depends on.
  • Environment dependency: a service, browser, network request, or test account behaves inconsistently.
  • Product defect: the application itself has a race condition or intermittent failure.

2. Prefer locators tied to user intent

Use accessible roles and names, labels, or a deliberate test ID. Avoid brittle selectors based on deep DOM structure or styling classes that change frequently.

const saveButton = page.getByRole('button', { name: 'Save changes' });
await saveButton.click();
await expect(page.getByText('Changes saved')).toBeVisible();

Make the locator unique and assert an outcome that matters to the user. If a page contains repeated controls, scope the locator to the relevant dialog, row, or section.

3. Wait for a meaningful application state

Fixed sleeps often make tests slower without making them reliable. Instead, wait for a visible state, a specific response, or a condition that indicates the workflow is ready. Use Playwright's auto-waiting and web-first assertions where they fit.

await expect(page.getByRole('heading', { name: 'Release details' })).toBeVisible();
await expect(page.getByRole('button', { name: 'Publish' })).toBeEnabled();

Do not treat network-idle as a universal readiness signal: applications with polling, analytics, or persistent connections may never become idle.

4. Isolate test data and state

Each test should establish the data it needs and clean up where appropriate. Avoid relying on execution order, shared mutable accounts, or records left by a previous run. Use unique test data when parallel workers could collide, and make setup repeatable.

5. Use traces to understand intermittent failures

When a failure occurs in CI, retain a trace and relevant screenshots or logs. Review the action timeline, DOM snapshots, console output, and network activity. Compare a passing run with a failing run instead of guessing at the cause.

6. Treat retries as diagnostics, not a fix

Retries can help reveal whether a failure is intermittent, but a test that passes only on retry still deserves investigation. Track flaky-test frequency and remove or quarantine a test only under a clear team policy.

Practical investigation checklist

  • Reproduce the failure locally or in a controlled CI run.
  • Identify the first incorrect state, not only the final timeout.
  • Check locator uniqueness and application readiness.
  • Confirm test data and account state are isolated.
  • Review traces, screenshots, console messages, and failed requests.
  • Run the corrected test repeatedly and in parallel when applicable.
  • Document the root cause and add coverage for the underlying defect if needed.
