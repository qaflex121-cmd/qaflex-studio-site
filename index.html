Practical QA checklists to get started

Quick references to adapt to your application's risks, requirements and team standards.

Playwright

Reliable test checklist

  • Prefer user-facing locators and stable test IDs where appropriate.
  • Wait for observable application states, not arbitrary timeouts.
  • Keep tests isolated and create their own required data.
  • Assert meaningful, user-visible outcomes.
  • Capture traces, screenshots or logs when diagnosing failures.

Download PDF checklist

API testing

API coverage checklist

  • Validate success and expected error status codes.
  • Check schema, required fields and data types.
  • Cover missing, invalid, boundary and unexpected inputs.
  • Verify authorization and role-based access.
  • Use synthetic or approved test data; never expose secrets.

Download PDF checklist

Test strategy

Release readiness checklist

  • Review scope, acceptance criteria and changed components.
  • Prioritize tests by business impact and risk.
  • Confirm critical journeys and integrations are covered.
  • Review open defects, severity and workarounds.
  • Record evidence, residual risks and release recommendation.

Actionable guidance across automation design, API quality and AI-assisted testing.

Automation engineering

How to reduce flaky Playwright tests

Classify failures: locator instability, asynchronous behaviour, shared test data, environment dependencies or genuine product defects.

  • Use resilient locators based on roles and labels.
  • Assert the state the user should observe.
  • Remove shared mutable state between tests.
  • Use traces to inspect the failure timeline.
API quality

What a useful API regression suite covers

Check more than HTTP 200: verify the contract, permissions, data integrity and failure behaviour.

  • Positive, negative and boundary scenarios.
  • Schema and response-field validation.
  • Authentication and authorization boundaries.
  • Safe, repeatable test data and cleanup.
AI in QA

Use AI for test design—with human review

AI can brainstorm scenarios and organize test ideas, but generated output needs validation against product behaviour.

  • Provide clear requirements and constraints.
  • Ask for edge cases and assumptions separately.
  • Check expected results with product knowledge.
  • Never paste credentials or sensitive production data.
